# outbox-bench

Сервис на Kora 1.2.23 (Kotlin, KSP, блокирующий код без корутин), который использует `kora-outbox` так, как это делал
бы продакшен-сервис. Он записывает заказы и их сообщения в одной транзакции, передаёт их через relay в Kafka и
потребляет обратно с дедупликацией через inbox и проверкой порядка заказов по каждому пользователю. Он не публикуется.

## Запуск

Поднимите стенд (`observability/docker-compose.yml` или любые Postgres 16 и Kafka, которые у вас есть), затем:

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew :bench:installDist
bench/build/install/bench/bin/bench
```

При старте приложение создаёт свои бизнес-таблицы и топик `orders` (12 партиций); оба шага идемпотентны. Таблицы:
`orders` (одна строка на заказ, с `message_id` — id, который вернул send в транзакции заказа), `user_seq`
(последовательность по пользователю), `bench_rolled_back` (id сообщений, чья транзакция откатилась, см.
`ROLLBACK_PERCENT`) и `bench_consumed` (впервые полученные сообщения заказов, дописываются в транзакции потребителя в
порядке коммитов). Таблицы outbox и inbox создаёт библиотека. Если топик уже существует с другим числом партиций,
приложение пишет WARN.

Postgres нужны `max_locks_per_transaction=256` и `max_connections=300` (compose-стенд задаёт обе настройки). Массовый
`sendAll` из 10 000 различных ключей держит 10 000 advisory-блокировок в одной транзакции. В общей таблице блокировок
`max_locks_per_transaction × max_connections` слотов, со значениями по умолчанию всего 6 400. Писатели, relay-воркеры и
потоки потребителя держат по соединению из пула.

Если вы очищаете `user_seq` (для чистого прогона), перезапустите и приложение: потребитель хранит в памяти последний
`seq` каждого пользователя и посчитал бы начавшиеся заново последовательности нарушениями порядка.

## Эндпоинты

Публичный порт 8080:

| Запрос | Действие |
|---|---|
| `POST /load?rate=&writers=&keys=&messagesPerTx=&payloadBytes=` | Запускает генератор нагрузки, заменяя уже работающую нагрузку. Пропущенные параметры берутся из `bench.load`. `rate` задаётся в сообщениях в секунду, `0` означает без ограничения. |
| `DELETE /load` | Останавливает нагрузку. |
| `POST /orders?userId=u1` | Создаёт один заказ. Трасса начинается с HTTP-запроса. |
| `POST /poison?count=1` | Отправляет payload больше `max.request.size`. Kafka их отвергает, и они переносятся в dead-таблицу. |
| `GET /stats` | Возвращает обработчик, текущие настройки нагрузки и счётчики бенчмарка в JSON (`failed` считает неудавшиеся транзакции писателей, `rolledBack` — намеренно откаченные). |

Приватный порт 8085: `/metrics` (Prometheus), `/system/readiness`, `/system/liveness`.

Режимы нагрузки:

- `messagesPerTx = 1` (режим заказов). Каждая транзакция берёт следующий `seq` пользователя из счётчика `user_seq`
  под блокировкой строки (и id заказа), отправляет сообщение и вставляет заказ с возвращённым id сообщения. Ключ —
  `u<0..keys-1>`. При `ROLLBACK_PERCENT` > 0 такая доля транзакций бросает исключение после отправки и откатывается;
  id сообщения тогда вставляется в `bench_rolled_back` отдельной транзакцией.
- `messagesPerTx > 1` (режим bulk). Каждая транзакция делает один `outbox.sendAll` из N сообщений с различными
  случайными UUID-ключами и не вставляет бизнес-строк. Это нагрузка сценария `bulk.sh`: 2 писателя × 10 000 сообщений
  на транзакцию, `payloadBytes=100`.

Каждая транзакция писателя выполняется под корневым span `bench.order.create`. Потребитель читает один poll на
транзакцию: один раз вызывает `inbox.tryAcceptAll` с `outbox-message-id` из poll, обрабатывает каждый впервые
увиденный id один раз и проверяет, что `seq` строго растёт по пользователю среди впервые полученных сообщений; та же
транзакция дописывает впервые полученные сообщения заказов в `bench_consumed`, чтобы проверку порядка можно было
повторить на SQL по всем инстансам и убийствам процессов. Bulk-сообщения несут `seq = 0`, и их порядок не
проверяется.

## Метрики

`bench.tx` (таймер транзакции писателя), `bench.tx.failed` (неудавшиеся транзакции писателей), `bench.tx.rolled_back`
(намеренные откаты), `bench.messages.sent`, `bench.consumer.received` (впервые полученные сообщения),
`bench.consumer.duplicates`, `bench.consumer.order_violations`, `bench.noop.delivered` (только для noop-обработчика).
Библиотека публикует собственные метрики `outbox.*`, а Kora добавляет метрики HTTP, JDBC, Kafka-потребителя и JVM.

## Конфигурация

`src/main/resources/application.conf`. У каждой настройки есть локальное значение по умолчанию, а переменные окружения
его переопределяют:

| Переменная | Ключ | По умолчанию |
|---|---|---|
| `POSTGRES_URL`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | `db.*` | `jdbc:postgresql://localhost:5432/outbox`, `outbox`, `outbox` |
| `DB_POOL_SIZE` | `db.maxPoolSize` | 48 |
| `KAFKA_BOOTSTRAP` | `bootstrap.servers` продюсера relay и потребителя | `localhost:9092` |
| `HTTP_PORT`, `METRICS_PORT` | `httpServer.publicApiHttpPort`, `privateApiHttpPort` | 8080, 8085 |
| `INSTANCE_NAME` | `instance`: `application_name` в Postgres и `service.instance.id` в трассах | `bench` |
| `OTLP_ENDPOINT` | `tracing.exporter.endpoint` (OTLP gRPC) | `http://localhost:4317` |
| `SERVICE_NAME` | `tracing.attributes."service.name"` | `outbox-bench` |
| `BENCH_HANDLER` | `bench.handler`: `kafka` или `noop` (считает и выбрасывает: чистая пропускная способность outbox) | `kafka` |
| `BENCH_TRACE_RATIO` | `bench.traceRatio`, доля сэмплирования корневых span; она же сэмплирует трассы, начатые HTTP-запросом, например `POST /orders` | 1.0 |
| `OUTBOX_SHARDS` | `outbox.shards` | 32 |
| `OUTBOX_RELAY_WORKERS` | `outbox.relay.workers` | 8 |
| `OUTBOX_RELAY_BATCH_SIZE` | `outbox.relay.batchSize` | 2000 |
| `OUTBOX_TABLE` | `outbox.table` | значение библиотеки по умолчанию, `outbox` |
| `OUTBOX_RELAY_MAX_TICKS`, `OUTBOX_RELAY_MIN_TICK`, `OUTBOX_RELAY_IDLE_POLL` | `outbox.relay.maxTicksPerBatch`, `minTickInterval`, `idlePollInterval` | значения библиотеки по умолчанию |
| `OUTBOX_XIDS_PER_PARTITION`, `OUTBOX_MAINTENANCE_INTERVAL` | `outbox.partitions.xidsPerPartition`, `maintenanceInterval` | значения библиотеки по умолчанию |
| `OUTBOX_CURSOR_ANCHOR_INTERVAL` | `outbox.relay.cursorAnchorInterval` | значение библиотеки по умолчанию |
| `HANDLER_DELAY_MS` | `bench.handlerDelayMs`: обработчик Kafka перед каждым `handleBatch` спит столько на каждую запись (прерывание обрывает сон: батч получает NotAttempted) | 0 |
| `ROLLBACK_PERCENT` | `bench.rollbackPercent`: доля заказов генератора нагрузки, откатываемых после отправки | 0 |
| `CONSUMER_THREADS` | `kafka.consumer.orders.threads` (`0` выключает потребителя) | 4 |
| `CONSUMER_MAX_POLL` | `kafka.consumer.orders.driverProperties."max.poll.records"` | 2000 |

Настройки продюсера (`outbox.kafka.driverProperties`): `linger.ms = 5`, `batch.size = 262144`, `compression.type = lz4`.
Значения `bench.load` по умолчанию: `rate = 0`, `writers = 8`, `keys = 10000`, `messagesPerTx = 1`, `payloadBytes = 300`.

## Сценарии

`bench/scenarios/run-all.sh` прогоняет все нагрузочные сценарии на compose-стенде и переписывает `bench/RESULTS.md`
(около 105 минут); каждый `bench/scenarios/<name>.sh` можно запустить и отдельно, тогда он дописывает свой раздел.
Сценарии сами запускают и останавливают приложение, поэтому сначала остановите работающий инстанс. Каждый прогон
отмечает свой интервал времени аннотацией Grafana с тегом `scenario`, использует новую таблицу outbox и пустой топик
`orders`, а после прогона удаляет таблицу. Логи приложения пишутся в `bench/build/scenarios/`.

Сценарии с одиночными сообщениями запускают потребителя с 12 потоками (по одному на партицию). После остановки
писателей сценарий ждёт, пока потребитель всё выберет (лаг группы 0, нет строк в retry-таблице, счётчики стабильны), и
только потом сверяет на SQL закоммиченные строки, которых нет ни в inbox, ни в dead-таблице, с числом закоммиченных по
счётчикам писателей. Обслуживание удаляет пройденные партиции, и их строки выпадают из проверки; такая частичная
проверка проходит, только если счётчик потреблённых сообщений равен этому числу. Любой другой исход (потребитель не
выбрал всё вовремя, строки пропали, частичная проверка, которую не покрывают счётчики, нечего проверять) печатается в
разделе вместо числа, оставляет таблицу outbox и завершает сценарий с ненулевым кодом, что останавливает `run-all.sh`.

`bench/scenarios/shard-cost.sh [ШАРДЫ...]` (или `RUNS="32 256 1024"`, по умолчанию 32; `run-all.sh` его не запускает)
измеряет, во что обходится число шардов на настройках библиотеки по умолчанию (relay workers 4 и `batchSize = 1000`
задаются явно, потому что у бенчмарк-приложения свои 8 и 2000): сначала фон стенда при остановленном приложении и
простой каждого числа шардов (xid/с, WAL B/с, коммитов/с), затем для каждого числа шардов bulk с обработчиком noop без
консьюмера (пропускная способность, задержка, CPU БД, WAL на доставленное сообщение, пакетов relay в секунду, размер
таблиц outbox в конце окна, в том числе на хранимое сообщение) и малую нагрузку 100 и 1000 msg/s, как в `low-load.sh`. `WARMUP` (60 с) и `STEADY` (180 с) задают прогрев и окно
каждого прогона; одно число шардов занимает около 18 минут. Длительность тика отдельно измеряет `TickCostBenchmark` из
модуля `outbox`, который не входит в обычную сборку: `./gradlew :outbox:test -Pbenchmark --tests '*TickCostBenchmark'`
запускает его на тестовом контейнере, а с `-Dbench.jdbcUrl=jdbc:postgresql://localhost:5432/outbox -Dbench.user=outbox
-Dbench.password=outbox` — на стенде; `-Dbench.shards` (32,256,1024), `-Dbench.ended` (0,100,400) и `-Dbench.rounds`
(200) задают сетку. Он печатает p50 и p99 запроса-пробы тика отдельно (только чтение, не зависит от fsync) и всей
записи тика, когда с предыдущего тика завершились E транзакций (без строк outbox или с одной строкой в каждой), а на стенде с `max_connections = 300` урезает E до свободных соединений и пишет
об этом в строке.

### Хаос и soak

`bench/scenarios/chaos-all.sh` прогоняет хаос-сценарии по порядку и останавливается на первом сбое: `chaos-kill`
(3 инстанса, `kill -9` каждые 20–60 с, 15 мин), `chaos-pg-restart`, `chaos-pg-pause` (30 с `docker pause`),
`chaos-kafka-restart` (по 5 мин каждый), `chaos-partition-churn` (крошечные диапазоны xid, убийства во время DDL
партиций, 10 мин), `chaos-small-pool`, `chaos-slow-handler` (по 5 мин каждый) и `chaos-soak` (60 мин). Всего около
2 ч 20 мин. Каждый сценарий дописывает раздел в `bench/RESULTS.md`, строку в
`bench/build/scenarios/chaos-summary.txt` и каждые 30 с пишет замеры в `bench/build/scenarios/chaos-<name>.csv`.
Инстансы работают бок о бок как `bench-1..3` на портах 8080–8082 (публичные) и 8085–8087 (`/metrics`; Prometheus
собирает метрики со всех трёх).

Они сверяют бизнес-таблицы, а не таблицу outbox (обслуживание удаляет пройденные партиции), после того как потребитель
всё выбрал (лаг группы 0, нет строк в retry-таблице, нет приостановленных шардов, курсор каждого шарда прошёл момент
остановки, счётчики не изменились при повторной проверке через 10 с): `lost` — заказы, для `message_id` которых нет
строки в inbox, `phantom` — id из `bench_rolled_back`, для которых она есть, нарушения порядка на SQL по
`bench_consumed` и по счётчикам потребителя, строки inbox этого прогона, которые не являются ни потреблённым заказом,
ни закоммиченным bulk-сообщением, и dead-таблица. Всё должно быть равно 0. Дубликаты подсчитываются и выводятся в
отчёт. Если потребитель не выбрал всё вовремя, печатается NOT DRAINED, а не число потерянных. Любой нечистый исход или
проваленная проверка сценария оставляет таблицы и завершает сценарий с ненулевым кодом.

### Безопасность

Скрипты посылают сигналы только процессам, которые запустили сами, по PID из `bench/build/scenarios/*.pid`, и только
после проверки, что этот PID всё ещё принадлежит их живому дочернему процессу. Действия Docker затрагивают только
контейнеры `kora-outbox-bench-*`; `run-all.sh` и `bulk.sh` также выполняют read-only `docker info`. Чтобы остановить
прогон, проверьте, что записанный процесс — всё ещё тот сценарий, который записал файл: `scenario.pid` содержит его PID
и время старта, а у переиспользованного PID время старта будет другим.

```bash
f=bench/build/scenarios/scenario.pid; { read -r p; IFS= read -r s; } < "$f"; [ "$(ps -o lstart= -p "$p")" = "$s" ] && kill "$p"
```

Сценарий снимает Postgres и Kafka с паузы или запускает их, если они на паузе или остановлены, останавливает свою
нагрузку и инстансы, закрывает свою аннотацию Grafana (с тегом `aborted`) и завершается с ненулевым кодом, что
завершает и `run-all.sh`, и `chaos-all.sh`.
